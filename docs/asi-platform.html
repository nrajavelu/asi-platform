System architecture

A retrieval-grounded pipeline, not a chat wrapper

Every request is traceable end to end: what was retrieved, what was assembled into context, what the AI Gateway generated, and what the guardrail verified before it reached a student.

01 · Ingestion

RAG Knowledge Pipeline

Turns raw filings and case PDFs into citation-addressable chunks.

  • Structure-aware chunking (10-K items, transcript turns, case sections)
  • Hybrid dense + keyword indexing per institution namespace
  • Every chunk keeps its source span for later citation checks
02 · Retrieval

Context Assembly Engine

Builds the exact context window the AI Gateway reasons over.

  • Top-k retrieval re-ranked against the student's live hypothesis
  • Prompt-template bundling: system role, rubric, retrieved spans
  • Prompt caching on static case content across a cohort's requests
03 · Reasoning

Aizentify AI Gateway

Runs the actual PESTLE↔SWOT analysis and Socratic turn.

  • JSON-mode output against a fixed strategy-matrix schema
  • Extended thinking for multi-hop macro→micro correlation
  • Escalation to a deeper-reasoning tier for faculty appeals
04 · Validation

Guardrail Engine

The only path to the student — nothing ships unchecked.

  • Every claim resolved against its cited source span, or rejected
  • Schema + rubric-threshold check before a score is recorded
  • Full prompt/response log kept for faculty audit and appeal
Knowledge base

What goes in, who puts it there, and what's just a record

Two different stores answer two different questions. The knowledge base is what the AI Gateway retrieves from to ground an answer — only faculty-provided source documents ever enter it. The activity record is everything that happens on top of it — every student hypothesis, every Socratic turn, every score — logged, timestamped, and never fed back into retrieval. Keeping them separate is what keeps grounding trustworthy: nothing a student writes becomes "fact" for the next student who opens the same case.

The knowledge base — vectorized

Only what faculty puts in: the case's source filings. Each one is chunked, embedded, and re-indexed the moment it's added — including mid-term, when a fresher filing replaces or supplements the original. This is the only material the AI Gateway is allowed to cite from when it grounds a claim.

The activity record — logged, not vectorized

Everything that happens on top of the case: every hypothesis, every Socratic exchange, every score, every faculty query. Timestamped and attributed, retained for the course's duration and beyond, and queryable by faculty or the institution at any time — the audit trail, not a source the Gateway reasons over.

When data actually moves

1

Course setup

Faculty uploads source filings and sets the rubric. Ingestion runs once, before any student sees the case.

2

Ongoing term

Students work cases; every hypothesis and dialogue turn is logged to the activity record in real time.

3

Mid-term refresh

Faculty can add a new filing — this quarter's 10-K — which re-triggers ingestion without touching the activity record.

4

Anytime after

Both stores stay queryable — faculty can audit any student's full trail, or review what the knowledge base contained on a given date.

Trust & governance

What a provost's office asks about first

The differentiator against a generic chatbot wrapper isn't the UI — it's that every one of these is enforced in the guardrail layer, not left to a system prompt's good behavior.

Zero-hallucination citation gate

Every factual claim in a matrix must resolve to a source span in the ingested document, or the Guardrail Engine rejects the output before it renders.

Socratic-only for graded work

The system prompt constrains the AI Gateway to questions and rubric feedback on scored submissions — it can guide, but it cannot hand a student the final classification.

FERPA-aware data handling

Student submissions and grades are never used for model training; encrypted at rest and in transit, with configurable data residency per institution.

Licensed content stays isolated

Case study and filing content lives in a per-institution vector namespace — no cross-tenant retrieval, ever.

Full audit trail

Every AI-generated grade carries its citation trail and prompt/response log, ready for a faculty appeal review.

Versioned model governance

System prompts and model versions are pinned and change-logged; the eval suite runs before any of them ship to a live cohort.

Rollout

A three-phase path onto campus

Scoped so the first checkpoint is a single course, one semester — proof before scale.

01

Pilot

One semester · one course
  • 5–8 cases from the existing course syllabus
  • Single faculty owner, one cohort of ~40 students
  • Success metric: grading turnaround and rubric-score correlation vs. manual grading
02

Department rollout

Two semesters · one department
  • Faculty case-authoring tools, no engineering support needed
  • Full LMS gradebook integration across sections
  • Success metric: faculty grading-hours reclaimed per term
03

Institution-wide

Year two onward
  • Live SEC filing and market-feed ingestion, always-current cases
  • Cross-course analytics for accreditation and assessment reporting
  • Success metric: adoption rate across the core strategy sequence
