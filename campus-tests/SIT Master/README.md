# SIT Master — Associate AI Engineer Campus Drive

Real, ready-to-use question paper sets for the actual test. Calibrated for
final-year engineering students at South Indian institutions, per the
assessment blueprint (Aizentify hiring blueprint artifact) built alongside
this content.

## What's here

| Folder | Sets | Format | Load with |
|---|---|---|---|
| `Aptitude/` | 7 sets (`set1_easy.xlsx` ... `set7_hard.xlsx`), 20 questions/30 min each | `.xlsx`, matches `load_questions.py`'s existing schema | Web UI → Question Bank → upload the `.xlsx`, **or** `python load_questions.py "SIT Master/Aptitude/set1_easy.xlsx"` |
| `Programming/` | 7 sets, 30 questions/60 min each | Same `.xlsx` format | Same as above |
| `Coding/` | 7 sets (`set1_easy/` ... `set7_hard/`), 15 questions/90 min each | One folder per set, one `.json` per question | **Important:** use `--replace` — see below |
| `Technical Discussion/` | 1 flat set, 17 questions across 4 areas | One `.json` per question | Web UI → Question Bank → Interview Question Bank → upload the `.json` files, **or** `python load_interview_questions.py "SIT Master/Technical Discussion/"` |

Set-type distribution across the 7 sets: **2 easy, 3 medium, 2 hard** (as
requested) — each set's internal question mix skews toward its label but
isn't 100% single-difficulty (e.g. an "easy" set is still ~15-20% harder
questions, so it still discriminates). The Technical Discussion set is not
tiered the same way (interviewer-scored rubric questions don't have a
correctness answer to calibrate difficulty against) - it's a flat 17
questions across `llm_api_experience`, `prompt_quality`, `git_workflow`,
and `vibe_coding`, matching the Programming set's AI/LLM-engineer focus.
A Technical Discussion round draws a random subset per candidate (default
4) from whatever's loaded.

## Loading a Coding set — read this before your first drive

`load_questions.py` (Aptitude/Programming) already **replaces the entire
bank** every time you load a file — so switching between sets there is
just "upload the next set."

`load_coding_questions.py` does **not** work that way by default — it's
additive, matched by question id, so old questions stay in the bank unless
removed. If you load Set 1's coding questions and then Set 2's without
clearing first, a round could randomly draw from **both** sets combined.

**Always use `--replace` when switching to a specific Coding set:**
```
python load_coding_questions.py --replace "SIT Master/Coding/set1_easy/"
```
Or via the web UI: Question Bank → Coding Question Bank → check "Replace
entire bank with just these files" before uploading that set's 15 `.json`
files.

## Topic weighting (matches the blueprint)

**Aptitude** (20Q): Quantitative 5, Logical Reasoning 5, Problem-Solving &
Analytical Thinking 4, Business Communication 3, Data Interpretation 3.

**Programming** (30Q): Programming/DSA 9, Git 4, REST APIs 4, AI/LLM
Concepts 5, Prompt Engineering 4, RAG/MCP Awareness 4.

**Coding** (15Q): Core DSA 7 (Python, Judge0), API Response Handling 3
(simulated LLM API contracts, no live network calls), Prompt Assembly 2
(deterministic string-formatting problems), SQL/Vector 3 (pgvector,
`<->` similarity queries).

## How correctness was verified

- **Aptitude Quant/Data Interpretation**: every answer is *computed*, not
  hand-typed — generated by running the actual arithmetic in Python.
- **Aptitude Logical/Problem-Solving/Business Communication**: hand-authored,
  checked for duplicate options and duplicate questions programmatically;
  every item was manually walked through for logical correctness (one
  genuinely underconstrained "hard" seating puzzle was caught this way and
  rewritten).
- **Programming DSA (MCQ)**: output-prediction questions ("what does this
  code print?") have their correct answer computed by *actually running*
  the snippet — never hand-calculated.
- **Coding DSA/API/Prompt problems**: every test case's expected output is
  computed by running the reference solution locally, **and** a
  representative spread across easy/medium/hard was additionally verified
  against the live Judge0 sandbox this content was built against.
- **Coding SQL/vector problems**: every single question's expected result
  was computed by running the actual reference query against a live
  pgvector instance (not a sample — every one), and a spread was
  additionally verified through the platform's real grading path
  (`sql_grader.run_sql_submission`, including its permission/timeout
  sandboxing).
- **Zero duplicate questions** across all 7 sets in every round type,
  verified programmatically (not just by construction) by loading every
  set through the real platform loader and diffing question text.

## Known limitation to flag to your team

SQL questions currently support exactly **one** test case per submission
(the platform's SQL grading is scoped to one fixed query, ordered-row
comparison) — this matches the platform's current design, not a defect in
this content.
